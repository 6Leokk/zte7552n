# 功耗测量(2026-10-13):方法、能测到什么、测不到什么

> 起因:用户要求「测试功耗,看功耗是否异常」。结论写在 §5。设备 = 原生 OpenWrt(path A),
> 自编 5.4.254 内核,插着 USB(既是管理口也是充电口)。

## 1. 只有一个传感器:sc27xx 电量计

设备上没有系统功率计。唯一能读的是 **sc27xx-fgu 库仑计/电流 ADC**:

```
/sys/class/power_supply/sc27xx-fgu/{capacity,voltage_now,current_now,temp}
/sys/class/power_supply/sc27xx-fgu/debug/dump_info   # cur_clbcnt 在这
/sys/class/power_supply/battery/current_now          # 同一个传感器
```

`bq2560x` 充电器**没有** ibus/vbus/ibat 测量值暴露出来(`/sys/class/power_supply/bq2560x_charger/`
只有 `constant_charge_current` / `input_current_limit` 等**设定值**,而且这两个读回来恒为 0,
是桩实现)。

## 2. 换算(对着驱动核对过,不是猜的)

`drivers/power/supply/sc27xx_fuel_gauge.c`:

```c
cap2clbcnt(cap) = total_mah*cap/1000 * 36 * cur_1000ma_adc * SC27XX_FGU_SAMPLE_HZ / 10
clbcnt2mah(c)   = (c*10/(36*SAMPLE_HZ) ± cur_1000ma_adc/2) / cur_1000ma_adc
```
两者互为逆运算,**1 clbcnt = 1/(7.2 × cur_1000ma_adc) mAh**。本机 `cur_1000ma_adc = 667`
(`init_clbcnt:12947270` 与 `cap2clbcnt(936) = 2695.7×36×667×2/10 = 12,946,9xx` 完全对上)。

于是:

```
mA = Δclbcnt / Δt(s) × 3600 / 4802.4 = Δclbcnt / Δt × 0.74963
```

## 3. 关键陷阱:**插着充电器时,这个传感器测不到系统功耗**

库仑计量的是**电池支路**。充电器插着时,bq2560x 从 VBUS 供给系统,电池只是浮着
(充电终止时净电流≈0)。此时读数是**仪表零点漂移**,不是系统功耗:

| 状态 | clbcnt 速率 | 折合 |
|---|---|---|
| 空闲,充电器在位 | **-13.0 counts/s** | **-9.7 mA** |
| 8 线程 CPU 满载,充电器在位 | -388 counts/s | -291 mA |

空闲 -9.7 mA 是**假的** —— 5 GHz AP(VHT80,信道 36,beacon 100ms)+ LTE 注册 + 屏幕背光
(255/255)不可能只有 43 mW。它就是零点漂移。满载那一行才是真的:负载大到超过充电器
「已充满」时的输出,电池被迫补差额,于是**电流 ADC 和库仑计同时**读数一致(-289000 µA vs -291 mA,
交叉验证成立,换算因子无误)。

## 4. 试过但**没用**的招:把充电器打成 HiZ,强制走电池

`bq2560x-charger.c` 支持输入高阻(EN_HIZ,系统走电池、VBUS 仍在、USB 链路不断):

```c
case POWER_SUPPLY_PROP_STATUS:
    if (val->intval == CM_POWER_PATH_DISABLE_CMD)   // = 9
        bq2560x_charger_set_power_path_status(info, false);   // EN_HIZ = 1
```
`status` 属性在 sysfs 里是 0644 + `property_is_writeable` 返回 1,所以
`echo 9 > /sys/class/power_supply/bq2560x_charger/status` **写入不报错**。
但**没有任何效果**:写完之后电池照样以 **+250 mA 充电**、电压照样爬到 4413 mV
(真进了 HiZ 的话充电器根本不可能输出)。`check_power_path_status()` 只在 probe 调一次,
不会来抢,所以不是「被改回去」,而是这次写**没能落到芯片上**。
→ **这条路不成立,别再试。**(顺带:`constant_charge_current` 写 300000 读回仍是 0,该属性是桩。)

## 5. 结论

- **可测的**:负载响应是真的、刻度是对的(满载让电池支路出 -291 mA ≈ 电池端 **1.25 W**,
  这是 CPU 满载相对充电器能供的部分被迫由电池补的差额)。
- **测不到的**:插着充电器时**系统实际功耗**。要真值必须**断开 USB 走电池**
  (此时库仑计才等于系统功耗)。
- 顺带得到的温度数据(充电器在位):SoC 空闲 **47.6 °C** → 8 线程满载 90 s 后 **55.5 °C**,
  board 45.7 → 53.6 °C;散热无明显异常,但满载温升 +8 °C。

**待办**:断 USB 跑 ~15 分钟,`/root/power-sample2.sh` 写 `/root/*.log`(在 ext4 上,重启不丢),
再插回读取 → 得到真实待机电流/功率。

全开,期间按 ~16 分钟一轮走"楔死 → 最后手段重启"(见 `sipa-wedge.md` §6.5,推算 20~25 次):

- (勘误:本节原把外出写成 13:49→21:46 共 7h57m —— 那是把 13:38 的"936‰/current_now=0"

## 7. "充电只有 0.5A"的根因与修复(2026-10-13 晚,实测通过)

症状:插着充电只有 0.19~0.8 A,而且**每次开机不一样**(用户报"只能 0.5A")。

根因(对着 `sqc_bq2560x.h` 的位定义逐个解码,不是猜的):

- 电池侧根本不是瓶颈:`REG02=0xa2` 是**芯片 POR 默认值**(驱动从不写 ICHG,`REG0B` reset
  后 POR 默认存活)。DT 里**没有** `constant-charge-current-max-microamp`(见 §10 勘误),
  电芯的最大充电电流规格在软件里不可读。两个都不是当时的限制。
- **瓶颈是输入限流 `REG00`(IINLIM,100+n×100 mA),由 probe 按 USB 检测设定**:
  本 rootfs 检测恒为 type=Unknown → `REG00=0x09`(**1.0 A**,实测电池得 ~0.8 A);
  SDP 误检测时 → 0x04(**500 mA**,对应实测 0.19 A 那种 boot —— 即"0.5A 充电")。
- `CONFIG_VENDOR_SQC_CHARGER=y` 把 power_supply 写入全变桩(rc=0 但不落芯片,
  `sqc_bq2560x.c:1835-1837`),唯一通路是 `device/registers` 直写 i2c。

修复(`charge-fix` 已扩展;每 boot 一次 + crontab 每分钟重钉):

| 寄存器 | 钉到 | 含义 | 实测 |
|---|---|---|---|
| REG0x00 | `0x0b` | IINLIM **1.2 A** | 电池电流 808 → **~950 mA** |
| REG0x02 | `0x90` | 保 BOOST_LIM=1.2A,ICHG=16×60=**960 mA**(保守天花板,**非电池规格**;见 §10) | 实测电芯入口限流到 ~0.8A(747-822mA)<960,这个钉子平时不咬 |
| REG0x03 | `0x22` | 原 ITERM 修复不变 | 94% 不再停充 |
| REG0x04 | `0x80` | VREG 4368 mV = 厂商驱动对这块电池自己的写值(§9) | 2026-10-13 实测芯片上曾躺着 `0x90`(4432 mV),来源不明的单次写入 |

- 幂等(值对了就不写),USB replug 后由 crontab 守卫拉回;实测 10 拍 ~940 mA 稳定,
  SSH 管理链路未受影响。
- 将来想要 >1A:改 `REG02` 一个字节即可(ICHG=25 → 1.5 A),但电芯规格不可验证 +
  热是硬约束(见 §10),本修复默认守 960 保守值。

## 8. 采样工具

`changxing60-linux/work/wedge-2026-10-13/power-sample2.sh`(设备上 `/root/power-sample2.sh`):

```sh
setsid /root/power-sample2.sh /root/power-idle.log /root/power-phase </dev/null &
```
必须 `setsid ... </dev/null &`,普通 `nohup ... &` 会随 ssh 会话一起死。相位标记文件
`/root/power-phase` 让日志里能看出哪一段是哪种状态(charger / hiz / burn)。

> 注意:满载测试如果用 `(while :; do :; done) &` 起 8 个,收尾要用 `jobs -p`;
> 本机 8 核跑满时负载均值会从 14 涨到 16,**不要把 load average 当负载指标**
> ——它有 10~14 是 vendor kthread 常驻 D 态的假象。

## 9. 对照安卓侧的三个问题(2026-10-13 晚:1.2A 会不会充坏 / 充电上限 / 旁路供电)

用户问:①输入提到 1.2A 不会充坏吧?②要不要设充电上限(比如 99%)防充坏?③有没有办法充满后旁路供电?
以下全部对着厂商自己的代码/DT 回答(就是我们这台的内核源码,安卓原厂跑同一套):

### 9.1 1.2A 输入:安全,且远在厂商设计值之内

- **1.2A 是"入口"限流(REG00 IINLIM),不是电池电流**。电池电流由 ICHG(REG02)单独封顶,
  我们钉在 960 mA——这是**保守选择,不是电池规格**:DT 里没有 `constant-charge-current-max-microamp`
  (见 §10 勘误)。入口 1.2A 的账:实测电芯 747-822 mA(**入口限流,ICHG 960 没咬到**)
  + ~0.4A 系统开销;1.0A 时电池只剩 ~0.8A。
- **厂商自己的设计余量**(DT `ums9620-2h10_feimao-overlay.dts`):
  `charge-dcp-current = <2000000 2500000>`(墙充输入 **2.0A**/上限 2.5A)、
  `charge-fchg = <3000000 2000000>`(快充档 **3.0A**)、CDP 1.5A、unknown 1.05A、SDP 0.5A。
  1.2A 输入只有墙充设计值的一半多一点。
- **芯片自己的保险**:REG06 VINDPM=4.5V——源撑不住时 VBUS 下垂,IC 自动降入口电流。
  实测 PC 口在 1.2A 下 VBUS 4.54~4.57V,离 4.5V 还有余量(见 charger-manager 的 vbus 打点)。
  ICHG 那个 0xa2(2.04A)从来不是驱动写的,是芯片 POR 默认值——厂商驱动根本不设 ICHG,
  安卓上是用户态守护经 SQC 投票再调的。
- 结论:入口 1.2A 远在厂商设计内(墙充 2.0A/快充 3.0A),VINDPM 4.5V 自保;
  (PC 口实测扛得住;换弱口会先触发 VINDPM 自降)。

### 9.2 99% 上限:机制已实现(charge-fix v3),但先说真话

**当晚顺手挖出一个比 99% 重要得多的问题**:实测 REG04=**0x90** → VREG code 18 = **4432 mV**,
比电池档案 4.34V 高 92mV,是谁写的查不到(dmesg 环形缓冲滚过了 probe 期),但实验证明是
一次性写入(手动改回 0x80 后 70s 无人再动)——若放着不管,充满就是真过压。这是"会不会
充坏"的真实风险所在,已由 charge-fix 每分钟钉死在 **0x80(4368mV)**,即厂商驱动
`set_termina_vol(4340)` 自己的取整结果——安卓原厂就充到这。

上限机制:charge-fix v3 读 `/opt/changxing60/charge-cap`(千分数,当前 **990**=99%):
到顶清 REG01[4] CHG_CONFIG 停充,掉 40‰ 再开。**实测通过**(2026-10-13):
- 临时把 cap 设 600(电池 697‰)→ 一分钟内 REG01=0x8a、status=Not charging、
  电池电流 **-1mA**;恢复 990 → REG01=0x9a,+847mA 重新充上;
- 随后整台机器经历一次假死重启(§sipa-wedge),**重启后五个钉(REG00/01/02/03/04)
  全部自动到位**、990 生效——"每 boot 恢复"也过了实测。

对"99% 防充坏"本身要诚实:99%≈4.33V,和 100%(4.37V 终止)差别很小,保护量有限;
**真想护电池改 800~900**(80%≈4.06V/90%≈4.15V,对应 OCV 表)。改法:一行
`echo 900 > /opt/changxing60/charge-cap`,或删掉该文件=完全不限。另外旧的"94% 停充"是
ITERM bug,不是保护特性,别混淆。

### 9.3 旁路供电:本来就是这样,无需设置

bq2560x 是 power-path 充电器:VBUS 在位时系统走 VBUS,电池只浮着。今晚的实测就是证据:
- 停充(CHG_CONFIG=0)后 SSH/热点照跑,**电池电流 -1mA**(±零漂)——板子全靠 VBUS;
- 更早的满载实验:8 线程烧机时电池才被迫补 -291mA,平时 0;
- 插电"充满"状态(13:38 的 936‰/current_now=0)就是它:充满即浮空,系统不耗电池。
所以"充满→旁路"是默认行为,上限(§9.2)只是把"浮空点"从 100% 挪到 99%。
不存在的是反向(强制走电池,HiZ 实验,§4 已证伪——也别需要)。

## 10. 勘误 + 2.04A/3A 全链路评估 + REG04 写入者定位(2026-10-13 深夜续)

> 起因:用户追问"0xa2(2.04A)是芯片 POR 默认,用它会不会充坏?全链路可行就提升上限,
> 能测到 3A 吗?要全流程,用最稳的做法。同时解决真风险。"查源码后发现上一版的
> "960 mA = 电池档案上限"是错的,这里勘误并回答。

### 10.1 勘误:960 mA 不是电池规格,是保守选择

- feimao 的电池 DT 节点(`ums9620-2h10_feimao-overlay.dts`,`bat: battery`,且**没有**
  基础 dts —— overlay 即全部定义)**没有** `constant-charge-current-max-microamp` 属性。
- `sprd_battery_info.c:862` 用 `of_property_read_u32` 读它,读不到就保持 `:778` 的默认
  `-EINVAL`(-22)。字段类型是 `int`(`sprd_battery_info.h:114` / `power_supply.h:373`)。
- 所以探测期 `current_max_ua = constant_charge_current_max_ua / 1000 = -22/1000 = 0`
  (`sqc_bq2560x.c:769`,有符号整除截断向 0)。`set_termina_cur(0)` 走 `cur<=60 → code 0`
  分支(`sqc_bq2560x.c:588`),本该写 ITERM=60mA(code 0)。
- 但实测探测后 REG03=`0x2f`(ITERM code 0xF=960mA)。**所以"探测把电池档案的 960 写成
  ITERM、被 clamp 成 0xF"这个旧解释是错的**——根本没有 960 这个值传进去。`0x2f` 最可能
  是**芯片 POR 默认值**(探测期的 `set_termina_cur` 写没生效,和下面 REG04=0x90 同款)。
  症状(ITERM 960mA → ~94% 停充)和修法(钉 0x22=180mA)不变,但根因叙述要改。
- **结论:REG02 ICHG 钉 960 mA 是 charge-fix 自己挑的保守天花板,不是电池规格。**
  没有这个规格可读,软件无法确认电芯的额定最大充电电流。

### 10.2 2.04A(0xa2)会不会充坏?全链路不可行,不提

用户问的 0xa2 是 **REG02 ICHG(电芯侧)**,不是入口。三个硬理由:

1. **实测:电芯现在是入口限流,提 ICHG 一点用没有。** 设备实时 `ibat=747-822 mA`,
   ICHG 上限 960 mA —— **747 < 960,电芯在入口瓶颈,不在 ICHG 瓶颈**。入口 1.2A 里
   系统吃 ~0.4A,电芯只剩 ~0.8A。把 ICHG 从 960 提到 2040,**电芯一个 mA 都不会多**
   (入口先到顶)。在 PC 口上提 ICHG 是空操作。
2. **热是硬约束。** factory-IR=252mΩ。2.04A 的 I²R=2.04²×0.252=**1.05W**;960mA 是
   0.23W。**4.5 倍热量**砸在电芯+充电 IC 上,口袋机无主动散热,实测 SoC 空闲就 47.6°C。
   这是"充坏"(鼓包/寿命骤降)的真实路径。
3. **电芯规格不可验证。** DT 无 cell max charge current,软件**无法确认** 2.04A(0.69C)
   在这块电芯的额定内。0.69C 对很多电芯能扛,但"大概率能扛"不是"最稳的做法"。

→ 全链路不可行,**ICHG 不提,维持 960 保守天花板**。

### 10.3 3A 呢?

DT `charge-fchg = <3000000 2000000>` 是**入口**快充档(3.0A),不是电芯电流。即便 3A
入口,电芯仍被 ICHG 封顶(960mA),**不会快充**——只是系统满载时电芯还能维持 960mA。
要 3A 入口得快充分墙充(D+/D- 识别),我们 USB 检测坏(恒 Unknown)识别不了,只能强制
写值。要真加速电芯充电=提 ICHG,踩 §10.2 的三条红线。

### 10.4 "真风险"(REG04=0x90)写入者定位 + 已处置

- **这 boot 没复发**:REG04=0x80(钉住),logread 里没有 `0x90 -> 0x80` 纠正记录 →
  这 boot 探测期 `set_termina_vol(4340→0x80)` 写成功了。
- **IR 补偿不是写入者**:`cm_ir_compensation`(`charger-manager-sqc-v8.c:2481`)是内核侧
  votable 投票(不依赖安卓守护进程),公式 `target = cell_CV + ibat×rc`,DT `ir-rc=20µΩ`。
  在 0.8A 下 target ≈ 4340+16 = 4356mV → **0x80**(跟钉子一致)。要到 0x90(4400mV)得
  ~3A 电流,我们远不到。所以 0x90 不是 IR 补偿在 0.8A 写的。
- **0x90 最可能是芯片 POR 默认值**在某次 boot 探测期 i2c 写失败后存活下来(那次
  `set_termina_vol` 没落芯片)。这解释了它为什么只出现过一次、是间歇的——和 §10.1 的
  REG03=0x2f 同款(POR 默认存活于探测期写失败),只是 REG04 的探测写多数 boot 能落、
  REG03 的探测写似乎多数 boot 都不落。
- **危害评估**:0x90=4432mV,低于 IR 上限 4.5V、低于 OVP 4.8V,但超 cell CV(4340)
  **92mV**。CC 阶段(大电流)有 IR 压降补偿、不超充;**CV/尾段(电流→0)无压降可补,会过充**
  ——这是真风险所在。
- **已"解决"**:charge-fix 每 boot + crontab 每分钟钉 0x80。若 0x90 复发,≤60s 内纠正
  并在 logread 记 `REG0x04 0x90 -> 0x80`。风险从"持续过充"降为"≤60s 瞬态"。要彻底定位
  写入者得禁钉 + 新鲜 boot 竞速读(会把电芯暴露给潜在 0x90),对只出现过一次、已钉住的
  风险不值当。

### 10.5 结论:最稳的做法 = 维持现状,不动

- ICHG 960mA(保守天花板,实际电芯只吃到 ~0.8A 入口限流)
- IINLIM 1.2A(PC 口实测 VBUS 4.54-4.57V,离 VINDPM 4.5V 余量已薄)
- REG04 钉 0x80(已处置间歇过充)

电芯在 PC 口已充到入口极限,**没有安全的提升空间**。

**唯一能"多充"的条件性选项**(不是加速电芯,是抗系统负载):换 ≥2A 墙充、走 WiFi 管理
(放弃 USB 管理口),把 IINLIM 提到 2.0A —— 热点+魔法满载时电芯仍能维持 960mA,不被
系统抢流。但 USB 检测坏=强制值,换回 PC 口前得手动降回 1.2A。要真加速电芯本身,没有
安全路径。

## 11. 省电策略(2026-10-15 实现,宿主侧已验,真机未验)

用户要求「最好对省电控制也有一定的策略」。基线是 §5/§6 那个数字:**整机平均 ~215 mA ≈ 0.8 W,
满电约 13 小时**——这台机当网关时,电去哪了基本是**蜂窝 + 热点 + 魔法**吃掉的,不是 AP 跑得快。

### 11.1 只动两个杠杆,而且都不碰数据通路

| 杠杆 | 做什么 | 默认 | 为什么选它 |
|---|---|---|---|
| CPU governor | 按配置钉(默认 `schedutil`) | **开** | 开机就有,零风险:唯一的副作用是调频策略,且设备本来就靠 vendor 的热区在限 |
| 内屏空闲熄背光 | 无人按键一段时间后背光归 0,**保留档位记忆** | **关**(0 = 从不) | 内屏是唯一"不服务网络却在耗电"的部件;但省多少**没测过**,所以默认不开 |

实现:

- `rootfs/overlay/opt/changxing60/bin/power-policy`(`apply` / `status`)、`openwrt/overlay/etc/init.d/changxing60-power`(S96);
  配置 `/etc/changxing60/power.conf` 里的 `governor=NAME`。
- 空闲熄屏在 `tools/screen/changxing60-screen.c`(背光和按键都归它管),配置 `/etc/changxing60/panel-idle`(秒);
  环境变量 `CHANGXING60_PANEL_IDLE` 可覆盖。

### 11.2 故意**不做**的事(这部分比做了的更重要)

- **不做 WiFi 发射功率回退。** 看着像最优杠杆,但**没有客户端连着的时候,正是最需要满功率让客户端
  找到 AP 的时候** —— 用加入时的距离换一个从没测过的省电数字,不划算。等有数再说。
- **不碰调制解调器 / 数据呼叫 / 热点。** 这台机每一次楔死都出在那条路上(`sipa-wedge.md`),
  为了省电去动它,风险与收益根本不成比例。
- **不做 CPU 频率钉死。** 只换 governor;厂商内核自己有温控档(`spectrum` 那套),`thermal-guard`
  也在,钉频率会和它们打架。

### 11.3 空闲熄屏的状态机:危险的是它**不该**做的事

熄屏本身一行代码,风险全在边界上,所以 `tools/screen/test-backlight.c` 里逐条钉住了:

- 熄屏**不改变**记忆的档位、**不重写**状态文件(`/etc/changxing60/backlight`) —— 否则"下次开机变暗"就是新 bug;
- 唤醒的**那一下按键不换档**,只把屏点亮;再按一下才正常步进;
- 用户**自己**选的"关"(档位 0)不被计时器抢功,也不会被它反复写 0;
- 配置为 0 时计时器**从不**触发(出厂默认即此,直到省电量被测出来为止);
- 环境变量 `CHANGXING60_PANEL_IDLE` 优先于文件,`=0` 保持关闭。

`tools/screen/test.sh` 全过。

### 11.4 `power-policy` 的宿主侧测试与它当场抓到的 bug

`tools/power/test-policy.sh`(新增)拿**真脚本**打在假 `/sys` 树上跑(policy 只认路径,不认设备):

- 提供该 governor 的 policy 被切换,**不提供的原样不动**(写一个 policy 不支持的 governor 会
  "写成功"却毫无效果,是**静默**那一种失败 —— 这条就是为它写的);
- `governor=performance` 这类配置真的生效;
- 谁都不提供的 governor 要**报错退出非零**,不能静默;
- **没有 cpufreq 的内核**上 `status`/`apply` 都要干净收场。

它当场抓到真 bug:`status()` 的最后一句是 `[ -r ... ] && echo`,在 shell 里**条件表达式成了函数返回值**
—— 于是任何没有电池/没有 wlan0 的设备上 `status` 都会 **exit 1**。已改成 `if/fi`(同一个错的写法在
`[ -z "$(policies)" ] && echo` 那行也在,一并改掉)。这正是"顺手写的 status 命令"最容易中的一刀。

### 11.5 还没做的(诚实列出)
- **省电量一个都没测。** 两个杠杆的效果都要上机测(`power-policy status` 前后对
  `sc27xx-fgu` 的 `current_now` 采样,方法见 §8)。**在测出来之前,`panel-idle` 保持默认关**。
- **`rmmod mali_kbase`(省 ~45 MiB)只在"确实不用 GPU"时才是省电档**,而用户明确要 GPU 正常
  (见 [`gpu.md`](gpu.md))—— 两者冲突,取用户要的那个。真要省电,做成 `power-policy` 的一档、
  由用户按需关,而不是默认关。
- **没有做 WiFi 侧的任何省电**(理由见 §11.2),也**没动蜂窝**。

## 12. 还有哪些东西在周期性地耗电(2026-10-16 增补)

§11 只讲策略;真正的"耗电项清单"——我们自己的看门狗(`cellwatch` 30 s、`hotspotwatch` 30 s、
`bootdiag` 每分钟、`charge-fix` 每分钟、内屏 `changxing60-screen` 2 s tick、`ndp-learn` 10 s)、系统基线、
以及**每一项准确的关停命令和关掉的代价**——整理在 [`watchers.md`](watchers.md)。要点:

- 稳态里最值得先关的是**内屏**(背光当前 255/255 + 2 s 唤醒,且不服务网络),其次是不用魔法时的 OpenClash;
- `cellwatch` / `hotspotwatch` **耗电很小但是保险**:「网没了」和「热点静默死」都只有它们会救 —— 省电时最后再动;
- 一个 procd 实例的关法是 `ubus call service delete '{"name":"changxing60-post","instance":"cellwatch"}'`,
  **别用 `/etc/init.d/changxing60-post restart`**(会把 `wififix` 一起重跑,真去 down/up 一次 AP);
- 设备上手改只用于一次性测量;要永久生效**改仓库**,否则下次 deploy 会被覆盖回去。
