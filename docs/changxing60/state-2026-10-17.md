## 6. 已挂起(2026-10-17 用户指示暂停,不再推进)

> **2026-10-17 补充判决**:同一天又把音频链路测到底了一次,三条单点根因猜想(AGDSP 无固件 /
> CP 没使能语音 / 数字增益 −60 dB)全部被实测打掉——第三条**是我们自己算错的**:厂商
> `audio_pga.xml` 每个通话场景都写 DG `0x18 = 24`,那条 ALSA TLV 是装饰,内核不做任何换算。
> 而"顶到 0 dB 重跑听测、用户回报『全是哑的』"那一轮**是被工具自己污染的**
> (`*_DSP MDG Set` 的 value[0] 是 mute,`tone-test.sh` 往里写了 1024)⇒ **那一轮什么都没排除**:
> 模拟/功放那一半既没被定罪,也没被洗清。**用户裁定:记录下来,这部分暂时不再适配**,
> 本节下面那段"二分实验"因此**没有执行**。全部证据与续做清单见
> [`telephony.md` §10](telephony.md)(§10.7 MDG 静音字段 / §10.8 参数生效时机分两族)。
>
> **对网络的影响:零。** 这一摊从头到尾只在 card 0 上动作,没有任何一处改动碰到 WAN/热点/转发;
> 而且**本轮没有把任何音频改动部署上机**(改过又 `git checkout` 回退了),设备上的音频行为与
> 本文件 §5 的版本构成完全一致。唯一需要知道的状态:今天测试在 mixer 里留下的几个值
> (`VBC_IIS_MASTER_ENALBE`、`VBC_IIS_MST_SEL_0_TYPE`、`VBC DAC0 DG Set 64,64`)
> **重启即回到 probe 默认**,不影响开机后的网络。
>
> **当晚状态(E1 上机同晚)**:S20 `changxing60-audio` 第一次真跑撞出开机 panic(E5,
> `conflicts.md` §10),**当天已修**(marker 门,主机 31/31 + 设备实测拒绝)。设备侧
> `vbc-load`/`vbc-dump`/`voice-audio` 维持 **644** = 本"挂起"裁定的开关(`[ -x ]` 守卫就是为此写的);
> 日后 `chmod +x` 回来**不会再炸**——冷启动路径已变成"跳读→写→置标→回读→验证",捡通话音频从这里起步即可。
> guard ko 在机(md5 `1ee9ed78…`,旧件备份 `/root/sprd-dmaengine-pcm.ko.pre-guard` = `e1fcb1db…`)。

**通话语音建立(接通后 ~8 秒被 CP 拆线)+「声音通道不对」。** 已掌握的事实:

- 断点在 **CP 侧**:`MSG_CP_VOICE = (0x35, 2)` 是 **DSP 通知我们** CP 的语音使能状态,
  `mask=0x0` = CP 说语音没使能;我们的 AP 侧 PCM(`hw:0,5` = `FE_ST_VOICE`)是**正常起来过的**。
- 声音不对至少有一半是设计使然:喇叭无功放驱动(必哑)、默认走听筒、DSP mode 表是**猜的**。
- **下一步实验(未执行)**:二分法 —— 停掉音频那一半再拨一通。
  若**照样几秒断** ⇒ CP/网络侧自己失败,与我们的音频程序无关;
  若**能保持**(只是没声)⇒ 是我们的音频路径把通话搞断的,根因在打开 PCM 的时机/参数。
  ⚠ 执行前必须先确认"怎么干净地只停音频一半"——这台机器上**两个进程同时读 `AT /dev/stty_nr1` 会把调制解调器弄哑到重启**。
